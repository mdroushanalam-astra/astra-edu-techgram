# EXECUTIVE ANSWERS (Part 28, placed first as directed)

**1. What have we built?** A working, tested, live-verified environmental
intelligence *backend* for India: 12 cities, 8 Place-State domains
(atmosphere, hazards, land, water, ecology, population, climate, energy),
a four-field epistemic envelope (knowledge_type, value_semantics,
query_extent, observation_basis), deterministic screening engines
(smoke/heat/runoff/flood), a spatial-relationship engine, an Evidence
Bundle, a hazard-event substrate (HazardEvent + OfficialAlert + five
voices), 22 verified external sources, and a 135-test suite that runs
green with the LLM key removed. A v1 frontend (6 views, 2,452 lines)
exists but consumes only the v1 API — the State/Energy/Hazards/Evidence
intelligence is currently **invisible to users**.

**2. Is Astra what we intended?** The architecture is *ahead* of the
original blueprint (it now has provenance semantics the blueprint never
imagined) and the *interface* is behind it (v1 UI predates the envelope).
The wedge — Project Impact & Site Screening — is implemented end-to-end
at the API level but its evidence richness is not surfaced.

**3. Current intelligence architecture:** WORLD → PROVIDERS (22) →
EPISTEMIC ENVELOPE → PLACE STATE (composition, never recompute) →
DETERMINISTIC ENGINES (frozen) → RELATIONSHIPS (spatial predicates) →
EVIDENCE (five voices, no-upgrade invariant) → SCENARIOS (orchestrated
engines) → HAZARD COMPOSITION (HazardEvent/OfficialAlert) → LLM
(explanation only, optional) → API (24 routes) → FRONTEND (v1 only).

**4. What works in reality?** Everything tested this audit returned
HTTP 200 with correct semantics: full Place State, energy, hazards
(USGS + FIRMS + flood case), evidence bundles, scenarios, PDF report,
Ask Astra (grounded, 10.8 s), onboarding pipeline, caches, fallbacks.
135/135 tests, twice (with and without LLM key). Frontend builds and
serves; its API proxy works.

**5. What doesn't?** Three latency paths (site-baseline **162 s cold**,
briefing 21 s cold — NDVI decade, scenario 18.7 s cold); the Evidence
route composes the **legacy hazards shape**, so its hazard block cannot
see live events (semantically wrong, numerically coincidental — P1);
grid state (CEA) unknown by design; smoke/flood/heat verification
impossible until a ground-truth source clears its gate.

**6. What is missing?** Frontend surfaces for the entire v2 intelligence
layer; a ground-truth verification source; environmental memory
(doctrine written, deliberately unbuilt); JRC GSW, Sentinel-5P, IMERG,
SACHET/IMD/CWC feeds (all gated or deferred).

**7. Biggest scientific limitation:** screening outputs are largely
**unverifiable today** — no in-situ ground truth is wired, so engine
calibration has no honest target (see docs/SELF_IMPROVEMENT_DOCTRINE.md §5).

**8. Biggest frontend limitation:** it renders Astra v1's feature-shaped
API, not Astra v2's epistemic State — no provenance, no unknown
distinguishable from zero, no evidence surfaces, not responsive.

**9. Biggest architectural risk:** the mismatch between backend honesty
and frontend impression. The backend says "screening, unknown,
lower-bound"; a dashboard inevitably reads as authority. Phase 5's
entire job is to close that gap (R1–R8), and the warning-authority
rules must carry into UI copy.

**10. Current differentiation:** cross-domain provenance-aware State +
epistemic envelope + evidence bundles + consequence composition. Data,
APIs, and maps are commodity; the representation discipline is not
(but see Part 22 for what is and is not yet a moat).

**11. What Astra is NOT:** a warning system, a forecast authority, an
EIA substitute, real-time monitoring, a disaster product, an LLM
product, and (today) a memory-ful system.

**12. Backend ready to freeze?** **Yes, conditionally** — one P1 wiring
correction (evidence-route hazards composition, ~2 lines) should be
authorized at the gate; everything else in docs/BACKEND_FREEZE_CHECKLIST.md
is safe-to-leave or deferred.

**13. Frontend ready to begin?** Yes, immediately after the freeze
checklist is signed: payloads are stable, types are the contract of
record, and every R1–R8 requirement has a verified backend behind it.

**14. What should Phase 5 build?** A State-native, envelope-generic
interface: domain-structured navigation over `/place/{slug}/state`,
provenance and temporal validity as first-class layout, evidence
surfaces, hazard five-voice UI with warning-authority separation,
energy/water/ecology surfaces, R5 responsiveness, R6 onboarding,
R7 comparison, R8 degradation states. Full blueprint: Part 24 +
docs/FRONTEND_AUDIT.md (v2).

# PART 5 — EPISTEMIC SYSTEM FORENSICS

**`knowledge_type`** (validated against a frozen tuple at construction):
- `observed` — the cited source reports it, *including source-run models*
  (CAMS, CMIP6, PVGIS, POWER). Never read as ground measurement.
- `inferred` — derived by Astra from provenance-bearing inputs
  (aggregates, spatial predicates, exposure counts).
- `scenario` — computed under a defined hypothetical by a frozen engine.
- `unknown` — value is null WITH a reason. The constructor **forces**
  this: a null value downgrades any claimed type to unknown and clears
  value_semantics and observation_basis.

**`observation_basis`** (7 values, primary-lineage rule): `in-situ`
(USGS — the only one), `remote-sensed` (Sentinel-2, FIRMS, POWER),
`model-derived` (CAMS, CMIP6, weather models), `reanalysis-derived`
(ERA5 archive, PVGIS-ERA5), `registry` (Census, Ramsar, geoBoundaries),
`crowdsourced` (OSM), `ml-derived` (Microsoft footprints). Primary
lineage = the mechanism the source's own documentation names as
dominant; mixed lineage is described in `method`/`limitations` — the
smoke index (fires × wind) carries null basis for exactly this reason.
Invalid values raise `ValueError` at construction.

**Temporal semantics:** `observed_at` (when the source produced it —
for CONTINUOUS sources like OSM this is Astra's retrieval time),
`valid_from`/`valid_until` (when the value holds — future windows for
CMIP6 decades, open for Census, exact analysis windows for POWER GHI),
`cadence` (hourly / continuous-upstream / static registry / decennial…).

**Spatial semantics:** `footprint` (what the value is valid for — a
grid cell, a district polygon, a point), `query_extent` (the bbox an
aggregate was computed over). Both present on capped counts, distinct
by design (the B3-inspection fix).

**`value_semantics`:** `exact` | `lower_bound`. Every capped Overpass
count (60-element cap) is marked `lower_bound` — live Delhi currently
reports `osm_power_substation_count = 60 [lower_bound]`.

**How false precision/fabrication is prevented (mechanisms, not hopes):**
fabricated zero ⇒ retrieval-statement rule + per-category Overpass
failure tracking (a failed query is unknown, never 0 — live-proven by
the OSM power *lines* category during 3.6B); source substitution ⇒
cross-source rule + separately enveloped channels (CAMS gap live-proved);
semantic upgrade ⇒ no-upgrade invariant tests on the bundle; provenance
loss ⇒ provenance-walk tests over every State item; scenario→observation
⇒ `scenario_item()` hardcodes knowledge_type scenario. **Concrete live
examples this audit:** energy State `solar_ghi_current = null (unknown,
"CAMS radiation feed returned no values at retrieval time")`;
`power_ghi_period_mean` unknown with the solar-lag reason while
`power_ghi_daily_mean = 5.18 kWh/m²/day` observed; hazards zero-event
rendering as a retrieval statement, not an existence claim.

# PART 7–8 — ENGINE FORENSICS (incl. smoke deep audit)

**smoke** (`scenarios/smoke.py`, 297 lines, read in full): wind-oriented
capsule (550 up/60 down/220 cross km) → FIRMS queried on capsule AABB →
hotspots filtered → FRP/50 MW emission weight (brightness fallback,
clamped 0.05–10) → mass-conserving Gaussian
`conc = w/(d·σ)·exp(−½(lateral/σ)²)`, σ = 0.14·d·env-multiplier
(min 1.2 km) → saturating absolute scale (REF 2.8e-4) → bands
low/moderate/high/severe → **dominant-fire arrival** (C1 fix verified in
code: `if conc > entry["dominant_conc"]`), suppressed below score 5 →
calm-wind skip at 0.5 km/h → TOP_FIRES=120 brightest-first cap →
exposure sums Census where known; **population_status**
complete/partial/unknown and `exposed_population = None` (never 0) when
high-exposure districts lack Census. Physically grounded: mass
conservation, 1/d² centreline (measured in INDEPENDENT_AUDIT).
Heuristic: σ rate, environment multipliers (coastal 1.15, mountainous
0.85), 12 h transport, no stability classes/plume rise/chemistry.
Does NOT claim: dispersion modelling, air-quality warnings, forecasts.
Tests: 12 invariants + 2 golden cases. **Live: available, 0 fires
(post-monsoon), window cached.**

**flood** (`estimate` read in full): DEM 5×5 low-lying share (within 2 m
of local min) + 24 h design storm scaled by pct + coastal/delta surge
*classification* (elevated ≥15% low-lying or min ≤5 m). NOT a forecast;
confidence Low. **heat:** linear −0.05 °C LST per green-% point
(published range 0.03–0.08), ×0.3 air transfer, always Low confidence.
**runoff:** SCS curve number (CN built 92/green 61/other 78/water 100,
soil group B assumed) → runoff depth + % change. Medium confidence.
**baseline:** WorldCover → S2 → OSM proxy chain (quality labelled).
**building validation:** land-normalised gate, population-anchored roof
band (15–35 m²/person × 0.2–3×) with recorded absolute fallback;
anti-circularity pin test. **relationships:** near/count-within-threshold,
explicit thresholds, geodesic approximation, knowledge_type inferred.
**hazard composition:** see Part 11. **Environment classification:**
curated per-city blocks + onboarded review_required flag.

# PART 17 — "WHAT HAVE WE ACTUALLY BUILT?" (the human reconstruction)

**What is Astra Climate?** An environmental intelligence system for
India that fuses 22 external sources into one provenance-bearing
representation of a place — what is observed, by whom, when, how
physically obtained, how far it holds, and what remains unknown — and
reasons over that representation with deterministic, labelled,
screening-grade engines.

**The problem:** Earth data is fragmented, unlabelled and unevenly
trustworthy; decisions (site screening, exposure, climate risk) need
fused, honest context, not another map.

**Core intelligence layer:** the epistemic envelope + Place State +
relationships + Evidence Bundle. The "intelligence" is the discipline:
every number carries its epistemics; composition can never upgrade a
claim; the LLM explains and never computes.

**vs a dashboard:** a dashboard shows values; Astra shows values *with
their types, dates, lineages, validity windows and reasons for absence*,
and composes cross-domain consequences with evidence chains.
**vs a chatbot:** the LLM is an interface; remove it and 100% of the
science survives (proven twice by drill).
**vs a weather API:** APIs return data; Astra returns *reconciled state*
across domains with conflict preservation (four GHI sources side by side).
**vs disaster-warning systems:** Astra represents official warnings and
computes independent context; it claims no warning authority (test-enforced).
**vs Copernicus/SACHET/IMD/CWC:** they are upstream authorities and
inputs; Astra is the cross-domain, provenance-aware consequence layer
on top — different layer, explicitly not competitors.

**Can do (verified):** 8-domain State for 12 cities; smoke/heat/runoff/
flood screening; hazard events + exposure; evidence bundles; scenario
orchestration; PDF reports; grounded AI Q&A; onboarding by name.
**Cannot do:** warnings, forecasts-of-record, engine verification
(no ground truth), environmental memory (by design, until deployment),
grid intelligence (no licensed feed), anything requiring the unbuilt
frontend surfaces. **Knows:** current state per domain. **Infers:**
aggregates, distances, exposure, bands. **Simulates:** three
interventions under labelled assumptions. **Explicitly does not know:**
grid state, official alerts, water level/quality, protected areas,
smoke arrival truth, flood outcomes — each with a written reason.

# PART 24 — FRONTEND IMPLEMENTATION BLUEPRINT (Phase 5)

Design law: **render the envelope generically.** One `<Value/>` component
consumes any enveloped item and renders: value + unit + knowledge-type
chip (observed/inferred/scenario/unknown) + observation date + validity
window + cadence + source + basis tag + lower-bound marker + unknown
reason. A new provider then requires zero UI redesign.

Information architecture (State-native, replaces feature-tabs):
**Place page** = identity header (place, environment class, data
freshness band) + domain navigation (Atmosphere / Hazards / Land /
Water / Ecology / Population / Climate / Energy) driven by
`/place/{slug}/state/{domain}` + cross-domain surfaces:
- **Hazards view**: five-voice layout — OFFICIAL (represented verbatim,
  visibly external) physically separated from OBSERVED events (map +
  list, snapshot labels) / INFERRED exposure / UNKNOWN reasons; urgent
  styling is reserved for official items only; Astra blocks are
  permanently labelled "Assessment (screening)".
- **Evidence view**: bundle viewer — scenario params, observations with
  retrieval statements, derived (scenario-styled), relationships chain,
  conclusion scope; the PDF report button.
- **Project Impact**: polygon draw → site baseline (with progress
  narrative for the 162 s cold path) → evidence → PDF.
- **Ask Astra**: grounded chat, answers quote their data block.
- **Onboarding**: name → live ingest progress → gate verdict (rejected
  states with reasons visible).
- **Comparison (R7)**: two places side-by-side per domain, envelope-aware.
- **Degradation states (R8)**: every `available:false` renders reason +
  fix; unknown renders its reason; stale renders its date.
Non-goals: no alert/notification UI, no prediction language, no
"safe/unsafe" copy (banned-vocabulary list applies to the frontend).
Build notes: code-split the >500 kB chunk; `api.ts` grows State/envelope
types mirroring backend payloads (types change together, tsc gates).
